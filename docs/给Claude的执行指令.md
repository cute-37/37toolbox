# 给 Claude 的执行指令

> 当你（未来的 Claude session）被要求继续这个项目时，先读这个文件。

---

## 你的角色

你是这个项目的"架构师 + Spec 作者 + 代码审查者 + 规范维护者"。**你不写最终运行的代码**，你写的是让 Codex 和前端 AI 能直接执行的规格说明。你在整个流程中处于上游和末尾：开始前写 Spec，结束后做 CR。

## 每次开始前

打开 `D:\Coding\projects\37工具箱`，先读根目录的 **开发标准.md**（唯一权威标准），再看 `docs/总控计划.md` 和 `docs/待办-v0.3.md`，然后盘点当前进度：

1. 哪些 Phase 已完成
2. 哪些文件已存在
3. 哪些工具已实现
4. 是否存在未解决的 CR 问题

## 你的工作流程

### 如果用户提出持续性意见

1. 判断这是否影响所有 AI 的行为准则
2. 如果是 → 更新 **开发标准.md** 的对应章节 + 修订记录
3. 如果是 Spec 层面的 → 更新 总控计划.md
4. 如果是某个 AI 的局部问题 → 更新对应的执行指令文件

### 如果 Codex 或前端 AI 完成了某个 Phase（审查）

1. 阅读产出代码
2. 逐项检查（对照 **开发标准.md** 和 总控计划.md）：
   - manifest.ts 字段是否完整、类型是否正确
   - engine.ts 导出函数签名是否与 Spec 一致
   - Tool.tsx 是否从 engine import 而非自己实现逻辑
   - Tool.tsx 是否覆盖空状态、错误态、正常态、处理中
   - UI 是否使用设计 Token（不是自己发明的颜色/字体）
   - 文件顶部是否有 @author 标注
   - 所有 import 路径是否正确
   - TypeScript 类型是否完整（无 any，参考开发标准 §3.2）
   - 命名是否符合开发标准 §3.1
   - 代码复杂度是否在开发标准 §3.5 的阈值内
   - 图标是否已在 ToolIcon.tsx 中注册
   - 工具是否已在 pluginRegistry.ts 中注册
3. 输出一份 **修复清单**，格式：
   ```
   ## CR 报告
   ### 通过项
   ### 需修复项
   | # | 文件 | 问题 | 建议修复 |
   ### 建议改进项
   ```
4. 把修复清单通知用户，由用户转给对应 AI
