# 37工具箱 开发规范

> **文档角色**: 本项目所有 AI（Claude / Codex / 前端 AI）的共同行为准则。违反本规范的代码不得合入。
> **更新机制**: 当用户在开发过程中提出影响全局的意见时，由 Claude 追加至本文档末尾的修订记录中并更新正文。Codex 和前端 AI 也可以提出规范建议，由 Claude 决定是否纳入。

## 一、命名规范

### 1.1 文件命名

| 类型 | 规范 | 示例 |
|------|------|------|
| React 组件 | PascalCase | `SidebarItem.tsx` |
| 工具入口 UI | PascalCase | `Tool.tsx` |
| 工具引擎 | 小写 | `engine.ts` |
| 工具清单 | 小写 | `manifest.ts` |
| 类型定义 | 小写 | `types.ts` |
| 样式文件 | 小写 | `globals.css` |
| 工具目录 | kebab-case | `json-formatter/` |
| Hook 文件 | use 前缀 + PascalCase | `useActiveTool.ts` |
| Store 文件 | 小写，语义化 | `appStore.ts` |
| Electron 文件 | 小写，语义化 | `main.ts`, `preload.ts` |
| IPC handler | 小写，{domain}Handlers | `fileHandlers.ts` |

### 1.2 变量与函数命名

- **常量**: UPPER_SNAKE_CASE，如 `MAX_PLUGIN_COUNT`
- **函数**: camelCase，动词开头，如 `formatJSON()`、`getActivePlugin()`
- **接口/类型**: PascalCase，名词，如 `ToolManifest`、`DownloadTask`
- **组件 Props 类型**: 组件名 + Props，如 `ButtonProps`
- **事件处理函数**: handle + 事件名，如 `handleClick`、`handleInputChange`
- **布尔变量**: is/has/can/should 前缀，如 `isLoading`、`hasSettings`
- **Zustand action**: 动词开头，如 `activateTool`、`toggleTheme`
- **Zustand selector**: get 前缀，如 `getFilteredPlugins`

### 1.3 目录结构语义

- `src/core/` — 只能放内核代码（PluginManager、类型定义、注册表），不放 UI
- `src/components/layout/` — 只放布局骨架组件（TopBar、Sidebar 等）
- `src/components/shared/` — 只放可复用的通用 UI 组件（Button、Input 等）
- `src/plugins/{tool-id}/` — 每个工具一个目录，包含 manifest.ts + engine.ts + Tool.tsx
- `src/stores/` — 只放 Zustand store
- `src/hooks/` — 只放自定义 hooks
- `src/styles/` — 只放全局样式文件
- `electron/` — 只放 Electron 主进程代码
- `resources/` — 只放静态资源（图片、字体）

## 二、TypeScript 规范

### 2.1 类型严格性

- **禁止 `any`**：除非是第三方库的类型缺口且无法补充，否则一律使用具体类型或 `unknown`
- **禁止 `as` 断言**：除非有明确的类型收窄理由，优先使用类型守卫（type guard）
- **所有函数必须有返回类型标注**：不管函数多简单，不允许省略返回类型
- **Props 类型单独定义**：不混合在组件定义中

```typescript
// ✅ 好的
interface ButtonProps {
  variant: 'primary' | 'secondary' | 'ghost';
  onClick: () => void;
}
const Button: React.FC<ButtonProps> = ({ variant, onClick }) => { ... };

// ❌ 坏的
const Button = ({ variant, onClick }: any) => { ... };
function getData(): any { ... }
```

### 2.2 导入顺序

文件内 import 按以下顺序分组，组间空一行：

1. React 相关（react, react-dom）
2. 第三方库（zustand, lucide-react 等）
3. 项目内核（`../../core/types` 等）
4. 项目共享组件（`../../components/shared` 等）
5. 同目录文件（`./engine`、`./manifest` 等）

```typescript
import React, { useState, useCallback } from 'react';

import { useStore } from '../../stores/appStore';
import type { ToolProps } from '../../core/types';

import { Button } from '../../components/shared';
import { manifest, formatJSON } from './engine';
```

### 2.3 类型与值分开导入

类型导入使用 `import type`，值导入使用 `import`：

```typescript
import type { ToolManifest } from '../../core/types';  // 类型
import { PluginManager } from '../../core/PluginManager';  // 值
```

## 三、代码风格

### 3.1 注释规范

- **文件顶部标注**: 每个文件第一行写归属

```typescript
// @author: codex | phase: 4a | tool: json-formatter | engine
// @author: frontend-ai | phase: 2 | component: Sidebar
// @author: claude | phase: 0 | spec: 总控计划
```

- **函数必须有 JSDoc**: 说明用途、参数、返回值

```typescript
/**
 * 格式化 JSON 字符串
 * @param input - 原始 JSON 字符串
 * @param indent - 缩进空格数，2 或 4
 * @returns 格式化结果或错误信息
 */
function formatJSON(input: string, indent: 2 | 4): JSONOutput { ... }
```

- **复杂逻辑加行内注释**: 说明为什么这么做，不是做了什么

```typescript
// 对大 JSON 做分块处理，避免阻塞主线程 > 200ms
const chunks = splitIntoChunks(input, CHUNK_SIZE);
```

### 3.2 空状态与错误处理

每个工具组件必须显式处理以下状态，不允许静默失败：

```
正常态 → 有输入有输出，正常工作
空状态 → 无输入或无数据，给出引导提示（如 "粘贴 JSON 到这里"）
错误态 → 输入无效或处理失败，红色提示 + 具体错误信息
处理中 → 异步操作进行中，显示 loading 指示器（如适用）
```

错误信息必须具体、可操作：

```typescript
// ✅ 好的
{ ok: false, error: 'JSON 解析失败：第 3 行第 15 列，缺少逗号', line: 3, column: 15 }

// ❌ 坏的
{ ok: false, error: 'Error' }
```

### 3.3 控制组件复杂度

- 单个 `Tool.tsx` 文件不超过 300 行（不含注释）。超过则拆分子组件到同目录下的 `components/` 子目录
- 共享组件不超过 150 行
- 引擎函数每个文件不超过 400 行
- 单个函数不超过 40 行

### 3.4 副作用隔离

- 引擎函数（engine.ts）必须是纯函数或无副作用的工具函数，不访问 DOM、localStorage、window
- 副作用（API 调用、文件读写、localStorage、剪贴板操作）只能在 React 组件中通过 hooks 或 IPC 调用

## 四、React 规范

### 4.1 组件定义

- 使用函数组件 + TypeScript
- Props 类型通过泛型传入

```typescript
const ToolName: React.FC<ToolProps> = ({ settings, onSettingsChange, onStatusChange, theme }) => {
  // ...
};
```

### 4.2 Hooks 使用

- useState 的初始值必须有明确的类型推导
- useEffect 必须有依赖数组，不得省略
- 自定义 hook 以 `use` 开头
- 不在条件语句或循环中调用 hooks

### 4.3 状态管理

- 工具自身 UI 状态用 useState（如输入框内容、折叠/展开状态）
- 跨工具共享的状态用 Zustand store（如当前激活工具、主题、搜索查询）
- 不要用 props 逐层传递全局状态——直接从 store 取

### 4.4 性能

- 工具组件使用 `React.lazy` 懒加载（由 PluginManager 的 loader 实现）
- 大列表使用 key（唯一 ID，不要用 index）
- 传递给子组件的回调使用 `useCallback`
- 高频更新的事件处理（如输入、拖拽）使用 debounce

## 五、样式与 UI 规范

### 5.1 颜色来源

**禁止在组件中使用硬编码色值**。所有颜色必须从 CSS 变量引用：

```css
/* ✅ 好的 */
background: var(--bg-secondary);
color: var(--text-primary);

/* ❌ 坏的 */
background: #222228;
color: #e4e4eb;
```

### 5.1.1 37 风格来源

- 项目名“37工具箱”的视觉灵感来自《重返未来：1999》的角色 37，但界面只做抽象引用，不直接使用角色图片、头像、台词或可识别版权素材。
- 允许使用的抽象元素：浅象牙/白金底、浅蓝银发感、哑金、青绿色点缀、古希腊几何秩序、轻量数学/星象细线纹理。
- 不允许把工具界面做成角色主题痛屏；工具可读性、密度和稳定性优先。
- 不允许将深蓝黑作为默认主题；默认主题必须是浅色 37 风格，暗色只能作为备用主题。
- 新增颜色必须先进入 `globals.css` 和 `tailwind.config.ts` token，再由组件引用。

### 5.2 Tailwind 使用

- 优先使用 Tailwind utility class
- 只有在 Tailwind 无法表达时才写自定义 CSS（如 CSS 变量引用、复杂动画）
- 自定义 CSS 写在 `globals.css` 的 `@layer components` 中，不要在组件中写 inline style

### 5.3 响应式

- 工具工作区宽于 600px：分栏布局
- 工具工作区窄于 600px：上下布局
- 使用 CSS 变量 + 相对单位，不写死像素值

### 5.4 主题

- 浅色 37 风格为默认主题
- 暗色主题通过 `.dark` class 切换 CSS 变量
- 组件通过 `theme` prop 感知当前主题，直接使用 CSS 变量即可，一般不需要写条件分支

### 5.5 可访问性

- 所有交互元素必须可通过键盘访问（Tab 键焦点环可见）
- focus-visible 环用 `--accent` 色，2px
- 按钮必须有明确的 `aria-label`（纯图标按钮）或可见文字
- 输入框必须有 label 或 `aria-label`

## 六、Electron 安全规范

### 6.1 渲染进程安全

- `nodeIntegration`: **必须设为 false**
- `contextIsolation`: **必须设为 true**
- 渲染进程不直接使用 Node.js API，所有系统调用通过 preload 桥接的 IPC
- 主窗口使用自绘中文标题栏和自定义窗口控制按钮，不能暴露系统默认英文菜单栏；需要系统菜单时也必须使用中文 label。

### 6.2 IPC 最小化

- preload.ts 只暴露渲染进程必需的 API
- 不在 preload 中暴露通用的 `ipcRenderer.invoke`
- 每个 IPC channel 有明确的输入输出类型

### 6.3 外部资源

- 不加载远程 URL（除非是下载工具的下载目标）
- 所有依赖打包进应用，不依赖 CDN
- 禁止使用 `eval()`、`new Function()` 等动态代码执行

## 七、测试与调试

### 7.1 开发验证

- 每次完成一个 Phase 后，`npm run dev` 必须不报错且窗口正常显示
- 每次完成一个工具后，手动测试：正常输入、空输入、非法输入、边界值

### 7.2 错误日志

- 所有 catch 块必须有有意义的日志输出（console.error + 用户可见的错误信息）
- Electron 主进程错误写入日志文件

### 7.3 构建验证

- `npm run build` 必须零报错、零警告（TS strict）
- `npm run package` 产出的安装包能正常安装和启动

## 九、协作纪律

### 9.1 不越界

- **Codex 不写 UI / CSS**（除了必要的 Tailwind 配置）
- **前端 AI 不写工具逻辑**（始终从 engine.ts import）
- **Claude 不写运行态代码**（只写 Spec / 类型 / 审查）
- Manifest 由 Codex 写（它是工具元信息的源头），前端 AI 只读

### 9.2 不假设

- 不确定的依赖版本号，使用现有 package.json 中的
- 不确定的目录路径，参考 总控计划.md §5
- 不确定的设计变量，参考 tailwind.config.ts 和 总控计划.md §4

### 9.3 不沉默

- 遇到 Spec 不清晰的地方，标记 `// TODO: 需要在总控计划中明确`
- 发现其他 AI 的代码有问题，记下来等 Claude 审查时统一处理（不要直接改别人的文件）
- 对规范有建议，通过 Claude 更新本文档

## 十、添加新工具

### 10.1 何时需要新工具

满足以下全部条件则创建新工具：
- 有一个独立、可描述的功能
- 功能的输入和输出是明确的
- 不需要修改内核代码

给已有工具新增能力（如密码生成器加"批量生成"）应修改现有工具的 engine.ts 和 Tool.tsx，而非创建新工具。

### 10.2 创建流程

详见 **添加新工具指南.md**，流程摘要：
1. 确定工具分类（需要新分类时同步更新 types.ts）
2. 创建 `src/plugins/{tool-id}/` 目录，含 manifest.ts + engine.ts + Tool.tsx
3. 在 pluginRegistry.ts 注册 lazy loader
4. 按检查清单逐项验证

### 10.3 新增分类标准

如果需要新增 ToolCategory：
- 现有工具中至少有 2 个能归入新分类
- 分类职责明确，不与现有分类重叠
- 同步更新 types.ts 的 ToolCategory、CATEGORY_LABELS、CATEGORY_ORDER
